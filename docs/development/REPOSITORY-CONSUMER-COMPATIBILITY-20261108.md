# Read-only repository consumer compatibility disposition

Compared Sch proposal `30996fbda89f5d1e3a9f26bd194b842185eba045` in `Schumpeter-repository-contract-20261108` with producer `e9a1d31140bcff34e3c9ef0f82f4b3dbca0ddd68`. This is source inspection, not new execution, consumer implementation, approval or package promotion. The [source inventory](repository-consumer-compatibility-20261108.json) hashes the exact inspected files and checks them against those commits. Existing accepted archives, user state and provider configuration were not accessed or changed.

The proposal's nine-key sidecar2/seven-key repository descriptor matches the producer. Top-level ready/workspace/admission remain mode2; explicit repository selection yields ready/workspace/admission mode3 with the existing eleven-key public repository capability. Admission/authorization envelope versions remain unchanged. Consumer-side immutable profile/root/approval/catalogue binding is additional Sch authority, not new producer wire fields.

The fixed runner subset also matches: `$node`, one relative script argument, optional entrypoint equal to that argument, input none, text output, write effect, exact empty-object input schema, and timeout100..30000ms. A consumer may require the optional entrypoint explicitly. The shared lease is within one managed host; there is no organization filesystem separation or cross-host lock. Script execution is unsandboxed and mutable transitive code is not pinned. Failed baseline plus a separate repair goal remains the accepted scenario; repeated effects and failed-run guards are unchanged.

The following producer preconditions must be explicit in the consumer helper:

- Invoke public `inspectProgramProxy` through the same verified bundled Node used for the host: `$node` resolves to `process.execPath`. It reads and hashes; it does not execute the selected checker. `manifestDigest` hashes exact manifest file bytes, `commandDigest` hashes the Node executable, and `entrypointDigest` hashes the selected script. Do not substitute a parsed/reformatted JSON hash for the first value.
- A fixed trusted helper may import inventoried `pida/dist/private-state.js` for `canonical` and `sha256`, exactly as the pinned repository helper does. This is an explicit e9 internal-module dependency, not a stable top-level SDK export. Full inventory/source verification and fixed import destinations precede invocation. No exported API change is necessary for this pinned consumer.
- `readRepositoryProfile` accepts optional trusted `runtimeBinding`. The stock e9 launcher does not pass it and does not independently compare the profile's claimed archive hash to `manifest.json`. The proposed inspection helper must pass the verified source/manifest tuple and preserve the parent's approval/provenance checks. A profile hash alone does not verify archive provenance or human approval.
- Private profile and manifest files are at most65536 bytes; selected script at most4MiB. Manifest name is bounded to100 characters, description1000, program ID to the lowercase producer identifier pattern. All required files must satisfy regular/single-link/path checks. Parent-owned protected locations still need the parent's explicit overlap checks.

The existing `GET /v1/project/file?path=...` returns exactly `{path,content,bytes,revision,truncated:false}`. `revision` is SHA256 of returned bytes; `content` uses fatal UTF-8 decoding with BOM preserved. Embedded NUL is rejected as `PROJECT_BINARY_UNSUPPORTED` even if the bytes are otherwise valid UTF-8. Native maximum is262144 bytes. The proposed128KiB consumer limit and bounded2MiB upstream JSON buffer do not require a producer change; consumer transport limits and strict byte roundtrip still need their own implementation tests. The read has no job ID parameter, authorship attestation, multi-file atomicity or exclusion of concurrent external writers. It must remain a capture-time byte observation, distinct from native ResultManifest, workbench revisions and final result text.

The proposal names older provisional catalogue dependencies. Root supplied accepted catalogue/Stop/frontend coordination pins `1cadaf`, `287a29d`, `a9` plus `dcf`; final dependency replacement and pairing are Sch-owned, not established by this producer inspection. Mode3 must not bypass their existing retained-context or Stop fences.

No new product tests were executed for this read-only check. Only source identity, document references and diff integrity were checked. General coding adequacy, performance and provider cost remain unknown. Retaining mode2 with no repository consumer is still the do-nothing alternative. This disposition expires for changed producer/source/wire/import pins; withdraw it if the consumer cannot bind the verified runtime and immutable approval tuple, introduces model-selected executable/argv/env, or labels live file bytes as native job-authored artifacts.

Conclusion: no producer wire incompatibility found in proposal30996fb; consumer implementation can reuse exact e9 subject to the listed preconditions and its separate review gates.
