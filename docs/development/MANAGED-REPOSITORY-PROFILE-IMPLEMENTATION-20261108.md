It reuses existing ProjectTools, ProjectView, ProgramRegistry, run leases and lifecycle. `src/agent-supervisor.ts` exposes admission capability3 (9 keys, including `repository_profile`). Private profile shape, nested fields, canonical digest and public projection are exactly the linked proposal. `runtime.source_commit`/`manifest_sha256` and approval receipt hash are trusted parent attestations, not proof of a human click or independent inventory verification by the child. The child's existing `source_digest` separately pins actual loaded source. `readRepositoryProfile` also accepts trusted `runtimeBinding` and `protectedPaths` API options; neither is a hidden JSON field or renderer option.

The launcher protects its known runtime/workspace/Node, provider workspace, selected Persona module, reference config/store/executable, absolute bridge-prefix files, catalogue entries, and profile/program manifest locations. The parent must reject overlap with its other private app paths before issuing approval. Root device/inode identity is checked at fresh start and resume, not advertised as continuous OS enforcement. ## Authority, environment and effects

Project read/write uses `trustedHost:false`; no `project_shell`, managed generic command tool, arbitrary model-selected executable/arguments/environment, or dependency installer is enabled. The separately approved ProgramRegistry proxy still uses its existing `trustedHost:true` invocation. The runner is generic: the test's `approved_check`/`checks/verify.mjs` names are fixtures, not a product-only checker.

Existing `src/program-proxy.ts:187` copies only the case-insensitive inherited environment names PATH, SYSTEMROOT, WINDIR, COMSPEC, PATHEXT, TEMP, TMP, TMPDIR, HOME, USERPROFILE, LOCALAPPDATA, APPDATA, PROGRAMFILES, PROGRAMFILES(X86), LANG and LC_ALL. ProgramRegistry supplies no explicit environment override. A synthetic actual child-process test checks that PIDA_SCHUMPETER_AUTH_TOKEN, PIDA_API_TOKEN and OPENAI_API_KEY are absent. No proxy environment semantics changed.

This is **not a sandbox or credential isolation boundary**. HOME/APPDATA/PATH remain present. The approved program has the OS user's filesystem/network privileges, may import mutable project source and may launch descendants. An entrypoint hash does not pin transitive imports or their effects; cwd is not filesystem confinement. Current ProgramProxy rechecks its direct approval before invocation, with no added parent-consent callback.

`single_writer: managed-host-run-lease/1` means one run at a time for the shared selected project within this workspace host. Two actual native agents were tested for serialization. It is not a cross-host/process lease, an external-editor exclusion, or per-organization filesystem isolation. Cancellation was tested after a synthetic runner created a marker: the proxy reports unknown effects, native organization cancellation stays authoritative, and the marker is not rolled back. No descendant-tree kill, transaction rollback or safe automatic replay is claimed.

## Independent review clarifications

The helper normalizes lexical dot/dot-dot path spellings with `resolve` before canonical realpath and directory-identity comparison; the original spelling remains part of the private profile digest. This is not a symlink/junction or root-identity bypass. The earlier canonical-path wording describes the resolved identity, not a requirement that all input spellings are already normalized.

The ProgramProxy allowlist above is the explicit forwarded environment, not an exhaustive list of names present in the final child. Independent Windows observation found HOMEDRIVE, HOMEPATH, LOGONSERVER, SYSTEMDRIVE, USERDOMAIN and USERNAME added by process/OS startup; a direct Node child control with only SystemRoot supplied reproduced them. Only names were recorded. Synthetic PIDA/provider/loader variables remained absent. No environment sandbox or broad credential-isolation claim follows from that test.
