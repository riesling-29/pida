# 여러 에이전트를 함께 보는 작업공간

작성: 2026-11-04 · Pida 전용 · **설계, 런타임 기능 구현 아님**

대조 기준: 로컬 `d0fa462d2c068e3e97c285199cb3bcb53c5293e5`, Pida 0.8.8 / Pi 1.2.0.
이 문서는 [공통 작업대 설계](SHARED-WORK-SURFACE-DESIGN.md)의 바깥쪽 운영 화면을 추가한다.
기존 작업대는 개별 작업을 자세히 보는 화면으로 유지한다. 다른 앱의 구현은 변경하지 않는다.

## 1. 제품 결정

**여러 에이전트를 켜 놓고, 필요한 작업을 나란히 보며, 개입할 곳만 찾아 들어간다.**

작업공간에는 탭이 있고, 탭에는 분할 패널이 있다. 패널은 특정 에이전트의 대화·현재 작업·파일·변경·검사·미리보기를 연다.
탭은 화면 묶음이며 에이전트가 아니다. 한 에이전트를 여러 패널이나 Web/TUI 양쪽에서 열어도 실행을 복제하지 않는다.
화면을 닫으면 관찰을 끝낸다. 작업 취소, 다음 작업 대기, 호스트 종료는 별도 동작이다.

TempleOS에서 차용한 제품 원칙은 구조와 현재 행동을 직접 드러내는 것이다.
에이전트 수만큼 채팅창을 무조건 펼치거나 장식적 상태 카드를 늘리지 않는다.
기본은 두 패널과 한 개의 집중 화면이며, 필요할 때 네 패널까지 나눈다.

## 2. 현재 재사용할 것과 빈자리

아래의 ‘있음’은 이번 코드 확인 결과다. 이번 턴에 실제 모델·다중 터미널을 실행한 결과가 아니다.

| 영역 | 현재 코드 | 필요한 연결 |
| --- | --- | --- |
| 실행 관리자 | `src/agent-supervisor.ts`: 영속 프로필·작업 큐, Pi runtime 생성, 작업 취소, pause/resume, interrupted 복구 | 기존 관리자를 공통 상태·조작 화면에 연결 |
| 동시성 | agent별 단일 실행, 같은 workspace key 직렬화, 전체 상한 | 실제 대기 이유·사용 자원 표시; 같은 checkout의 병렬 쓰기 금지 유지 |
| 호스트 구성 | `src/workspace.ts`: workspace 기본 상한 3, agent runtime 생성·정리, 활성 구성 inventory | 런타임의 적재 여부·구성 revision·권한·작업 경계 읽기 모델 |
| Client/API | `src/client.ts`, `src/server.ts`: agent/job 조회·접수·취소·steer·복구·증거 | 기존 owner 검사와 API를 우선 재사용; 없는 집계 필드만 추가 |
| Web | `examples/web/agents.js`: 에이전트 목록과 단일 `selectedId` / `selectedJobId` | 패널별 독립 선택, 탭, 분할, 지연 응답의 교차 반영 방지 |
| TUI | `src/tui-controller.ts`: 현재 선택한 주 세션과 파일·개요 화면 | persistent-agent 목록·job 선택·관리 동작, 다중 패널 연결 |
| 작업대 | 공통 작업대 문서의 대상·요청·변경·검증 계약 | 에이전트 소유 자원과 main/Studio 자원을 명시적으로 구분 |

상주 프로필은 항상 모델을 호출하는 프로세스라는 뜻이 아니다. Supervisor는 필요할 때 Pi runtime을 만들고 재사용한다.
현재 같은 Pida 호스트 안에서 관리하는 runtime을 에이전트별 OS 데몬처럼 표시하지 않는다.
클라이언트가 닫혀도 호스트가 살아 있으면 작업은 계속된다. 호스트 종료·재시작까지 동일한 실행이 살아남는다는 뜻은 아니다.

## 3. 화면 구조

### Web

- 상단: 연결한 호스트와 작업공간, 작업 탭, 실행 관리 진입점.
- 왼쪽: 에이전트 이름·현재 작업·상태. 복구 필요, 결정 필요, 실패, 새 완료를 우선 드러낸다.
- 가운데: 탭별 1/2/4개 패널. 각 패널에서 에이전트와 작업을 지정하고 대화·변경·검사·미리보기를 선택한다.
- 패널 머리: 실제 대상 에이전트, 작업, 프로젝트를 짧게 표시. 내부 ID는 상세에서 확인한다.
- 실행 관리: 현재 실행과 큐, 대기 이유, 실행 한도, 권한/도구/모델 구성, 복구 작업을 한곳에서 본다.

예: ‘개발’ 탭에는 UI 개발자와 테스트 담당을 나란히, ‘검토’ 탭에는 같은 UI 개발자의 변경과 검사 근거를 연다.
검토 탭을 만든다고 세 번째 에이전트가 생기지 않는다. 작업공간 선택도 임의 경로 입력이 아니라 호스트가 허용한 바인딩 선택이다.

### TUI

같은 agent/job/run을 여는 터미널 표현이다. Pi TUI의 입력·레이아웃 컴포넌트를 재사용한다.
목록과 작업 탭은 키보드로 이동하고, F1 메뉴에서 패널 열기·분할·집중·실행 관리를 발견할 수 있게 한다.
기존 입력·F키와 충돌하는 전역 키는 구현 전에 대조한다. Herdr/tmux의 prefix 키를 임의로 점유하지 않는다.
넓은 터미널은 두 패널, 충분한 너비에서는 네 패널을 허용한다. 80열에서는 선택 패널 하나와 나머지의 상태 목록을 유지한다.
resize는 실행을 다시 시작하지 않는다. 터미널 폰트는 사용자 터미널 설정을 따른다.

색은 기존에 선택한 거의 검은 녹색 배경과 밝은 회녹색 글자를 유지한다.
Web의 IBM Plex 계열 폰트는 폐쇄망에서도 외부 CDN 없이 사용할 수 있는 배포 방식과 라이선스를 확인해 적용한다.
이번 대화 시안에서 CDN으로 보이는 폰트가 실제 앱에 이미 번들되었다고 주장하지 않는다.

## 4. 화면과 실행의 소유권

| 객체 | 소유와 의미 |
| --- | --- |
| 호스트/작업공간 바인딩 | 인증한 연결과 호스트가 허용한 실행 자원. 표시 이름·로컬 경로를 권한으로 사용하지 않음 |
| agent / session / job / run | 호스트 소유의 실제 식별자. agent 이름이나 탭 번호로 추측하지 않음 |
| tab / pane | 클라이언트의 화면 배치·초점. 실행 및 취소 권한을 부여하지 않음 |
| 미전송 초안 | 해당 클라이언트와 대상 바인딩에 보존. 다른 에이전트로 전환해도 자동 전송/이동하지 않음 |
| 접수한 요청 | 호스트 소유의 고정 대상·요청 ID·job/run 기록. 창을 옮겨도 변경되지 않음 |

패널 참조 초안은 `connection_id`, `workspace_binding_id`, `surface_owner`, 선택적 `agent_id`,
`session_id`, `job_id`, `run_id`, `view_kind`, `work_target_ref`로 구성한다.
이름은 계약 확정 전 후보이며 현재 API 필드로 오해하지 않는다. surface owner는 main/Studio/agent를 식별한다.
현재 job 추적과 특정 과거 job 고정은 구분한다. 뒤늦게 도착한 응답은 현재 참조·revision과 맞는 패널에만 반영한다.
같은 자원의 구독은 클라이언트 안에서 공유해 패널 수만큼 폴링·이벤트를 복제하지 않는다.

Web/TUI는 실행 ID를 공유하되 레이아웃·선택·‘읽음’ 상태를 서로 강제로 동기화하지 않는다.
화면 복원 시 사라진/권한이 바뀐 자원은 unavailable로 표시하고 새 실행을 생성하지 않는다.
레이아웃 기록에 토큰·인증 헤더·원문 요청·도구 출력을 저장하지 않는다. 초안 보존 정책은 별도로 명시한다.

## 5. 런타임 관리의 의미

| 조작/표시 | 정확한 의미 |
| --- | --- |
| 패널·탭 닫기 | 해당 화면만 분리. 작업 취소/프로필 삭제 없음 |
| 다음 작업 대기 | agent 큐의 새 작업 시작만 중지. 이미 실행 중인 작업은 유지 |
| 작업 취소 | 지정된 agent/job/run만 취소 요청. 실제 종료 상태 수신 전 ‘취소 요청 중’ |
| 다시 접속 | 기존 상태 재조회. 마지막 요청을 자동 재전송하지 않음 |
| 복구 | interrupted 작업의 실제 산출물·외부 효과를 확인한 뒤 기존 reconcile/resume 계약 사용 |
| 호스트 종료 | 모든 runtime에 영향을 주는 별도 관리 동작. 단순 탭 닫기에 연결하지 않음 |

에이전트 생성은 프로필 생성과 첫 작업 접수를 구분한다. persona·도구·모델·프로젝트 프리셋은
호스트가 실제로 지원하는 선택지만 제공한다. 0.8.9에서 일반/호스트 설치 Persona 연결의 에이전트별 선택을
프로필·실행·HTTP·Web에 연결했다. [구현과 검증 범위](MIXED-PERSONA-0.8.9.md)를 참조한다.
이는 다중 패널이나 에이전트별 모델·도구·프로젝트 선택까지 구현했다는 뜻은 아니다.

실행 상태와 결과를 하나의 초록색 뱃지로 합치지 않는다.

- 연결/관측: 연결됨, 재접속 중, 마지막 확인 시각, 현재 상태 미확인.
- 큐/실행: idle, queued, running, paused, reconciliation required와 구체적 대기 이유.
- 작업 결과: completed, failed, cancelled, interrupted, limited 등 실제 job 결과.
- 검증: manifest의 VERIFIED/FAILED/UNKNOWN 등 실제 계약 값과 근거의 신선도.
- 새 완료: 클라이언트가 아직 확인하지 않은 결과. 성공이나 검증 통과를 뜻하지 않음.

모델 응답이 늦어도 마지막 신호만 낡았다는 이유로 실패 처리하지 않는다.
실행 한도와 대기 이유는 host의 실제 admission 결정에서 얻는다. 현재 active count로 원인을 추측하지 않는다.
토큰·비용·프로세스 지표도 실제 관측된 항목만 표시한다. 모르는 비용은 0원이 아니다.

## 6. 동시 작업과 기존 실행 경계

현재 `AgentSupervisor`는 같은 agent 또는 workspace key의 작업을 겹쳐 실행하지 않는다.
project를 켠 workspace에서는 main과 상주 agent가 공유 프로젝트의 실행 게이트를 사용한다.
따라서 여러 에이전트가 보여도 동일 checkout의 변경 작업은 대기할 수 있다. 이 이유를 UI에서 숨기지 않는다.

서로 독립된 작업공간에서는 기존 동시 실행 상한을 활용한다. 같은 저장소의 병렬 개발은 후속 단계에서
호스트 소유 worktree/branch 할당, 변경 출처, diff·검사·충돌·정리·통합 동작을 함께 설계한다.
worktree는 실행 디렉터리를 분리할 뿐 포트·데이터베이스·네트워크 부작용이나 보안 격리까지 제공하지 않는다.
‘병렬 실행’ 버튼으로 공유 프로젝트 잠금을 우회하지 않는다. 실패 후 불확실한 효과의 중복 실행 방지도 유지한다.

Pida는 단일 호스트의 작업 실행과 관찰을 담당한다. 조직 수준 임무 오케스트레이션, 다른 앱의 기억·분석 엔진은 추가하지 않는다.

## 7. Herdr에서 가져올 것

공식 [Concepts](https://herdr.dev/tui/docs/concepts/)와
[Agent automation](https://herdr.dev/tui/docs/agent-automation/)을 2026-11-04에 확인했다. 설치·실행 검증은 하지 않았다.

- workspace / tab / pane의 배치 계층과 agent lifecycle을 분리하는 원칙.
- 여러 작업의 상태를 위로 모으고 입력·개입이 필요한 곳을 찾는 탐색 구조.
- 클라이언트 분리와 실행 수명 분리, 완료의 클라이언트별 읽음 상태.

차이도 보존한다. Herdr pane은 실제 터미널이고 agent는 그 안에서 인식한 프로세스다.
Pida의 첫 구현은 구조화된 API로 여는 작업 패널이다. 완전한 PTY/셸을 제공한다고 부르지 않는다.
Pida 내부 상태는 Supervisor/Pi 이벤트에서 읽으며 화면 문자열로 추측하지 않는다.
Herdr의 server session namespace를 Pi conversation session과 같은 것으로 취급하지 않는다.

Codex/OpenCode 등 외부 실행자를 함께 열 필요가 생기면 Herdr 연계나 기존 PTY 호스트 재사용을 별도 어댑터로 검토한다.
각 어댑터는 attach·관측·입력·취소·복원·증거 capabilities와 실제 권한 경계를 명시한다.
지원하지 않는 동작은 unavailable로 남긴다. raw terminal 출력의 ‘완료’ 글자를 Pida의 VERIFIED 결과로 승격하지 않는다.
이번에는 Rust multiplexer를 복제하거나 Pi 실행 루프를 교체하지 않는다.

## 8. 기존 계획에 추가할 구현 순서

WS-01~07을 다시 만들지 않는다. 에이전트 소유 경계를 WS-01/02에 먼저 합친 뒤 화면 작업을 진행한다.

| 묶음 | 구현 범위 | 주 경로/재사용 | 종료 기준 |
| --- | --- | --- | --- |
| MA-01 공통 상태와 식별자 | owner-aware 패널 참조, 상태/대기 이유 projection, 정확한 job/run 조작 | supervisor, server, client, WS-01/02 | 다른 agent·낡은 run·권한 경계 시험; 조회로 새 실행 없음 |
| MA-02 공통 에이전트 관리 | Web 선택 상태 분리, TUI 목록·작업·pause/cancel/recovery 연결 | 기존 agent APIs, Web agents, TUI controller | 양쪽에서 동일 agent/job 관찰·제어, 새 실행 중복 없음 |
| MA-03 탭과 분할 | 패널별 초안·뷰·초점, 닫기/집중/복원, 구독 공유, 좁은 화면 | 기존 Pi TUI 컴포넌트, WS-03/04 | 2~4패널의 선택/출력이 섞이지 않음; 닫아도 실행 지속 |
| MA-04 운영 통합 | 설정 inventory·실행 한도·잠금 대기·interrupted 복구와 근거 | 기존 composition/recovery/manifest, WS-05/07 | detach·재접속·호스트 재시작·취소 실제 통합 시험 |
| MA-05 선택적 병렬 개발 | 별도 프로젝트/worktree 바인딩과 통합/정리 | host 프로젝트 게이트·Git/명령 경계 | 격리 작업과 같은 checkout 직렬화 확인; 권한 우회 없음 |

외부 Herdr/PTY 어댑터는 위 Pida-native 경로가 실사용된 뒤 별도 수용 기준으로 다룬다.
버전은 구현 묶음이 완성될 때 부여하며 이 설계 변경만으로 package 버전을 올리지 않는다.

## 9. 수용 기준과 완료 구분

필수 검증은 두 agent와 같은 agent의 두 패널을 모두 포함한다. 탭 전환 중 늦은 응답, 미전송 초안,
같은 checkout 대기, 서로 다른 작업공간의 동시 실행, 취소의 정확한 대상, 연결 단절과 stale 상태,
호스트 재시작의 interrupted/reconcile, Web↔TUI 동일 작업 접근을 재현한다.
실모델·실제 브라우저·PTY·Windows/회사 connector 시험은 각각 실행 여부와 결과를 보고한다.

- **계획 완료:** 코드 대조, 레이아웃/실행 경계, 재사용 경로, 패치 순서, 수용 기준.
- **시안:** 예시 데이터로 탭·분할·집중·실행 관리의 관계를 확인하는 대화 내 화면.
- **기능 구현:** MA-01~05 미구현. 기존 Supervisor 기능은 이미 존재하지만 새 다중 패널 UI와 연결되지 않음.
- **실제 통합:** 이번 설계의 다중 패널·실모델·Web/TUI/PTY 통합은 NOT_RUN.

시안의 샘플 상태 변화는 실제 agent 제어 또는 시험 증거가 아니다.

시안 확인: Node의 JavaScript 구문 검사와 DOM fixture에서 마크업 균형, 분할, 클라이언트별 배치,
탭 생성/닫기, 패널 닫기, 동일 agent의 변경/검사 보기, 집중, 실행 관리, 큐 대기/재개,
agent/view 바인딩을 확인했다. 실행 명령은 작업 환경의 `node check-multi-agent-design.mjs`다.
브라우저 렌더링·실제 terminal PTY·Pida API/LLM 시험은 이 검사에 포함되지 않는다.
runtime 코드를 바꾸지 않았으므로 기존 전체 테스트를 재실행하지 않았다.
