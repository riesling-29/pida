# 함께 보는 작업대 — Web / TUI 공통 설계

작성: 2026-11-04 · 범위: Pida만 · 상태: **설계, 아직 기능 구현 아님**

대조 기준: 로컬 `6221cde597db4562633c1d84c00d7610856b43db`, Pida `0.8.8`, Pi `1.2.0`.
연결된 draft PR의 기준 HEAD는 `0001c168328e5e4fe97d786403f724f5fbe44880`이다.
이 문서는 다음 개발의 계약과 수용 기준이다. 버전 승격, 실행 엔진 변경, 배포를 포함하지 않는다.

## 1. 제품 결정

**작업 대상을 보면서 선택하고, 그 대상에 요청을 붙이고, 실제 변경과 검증을 같은 자리에서 확인한다.**

Web과 TUI는 같은 호스트의 같은 세션·실행·작업 대상 기록을 여는 두 인터페이스다.
Web은 화면과 시각적 결과를, TUI는 파일·코드·명령 결과를 주 작업 대상으로 삼는다.
터미널에 브라우저를 흉내 내거나 두 화면에 각각 에이전트 엔진을 만들지 않는다.

대표 작업은 “현재 설비 화면에 점검 알림을 붙여줘. 검색과 필터는 유지해줘”다.
사용자는 대상과 보존 조건을 정한다. 에이전트는 허용된 도구로 구현한다.
사용자는 변경된 위치, 검사 근거, 남은 불확실성을 보고 다음 요청을 이어간다.
일반 저장소의 오류 수정, 테스트 보완, 등록된 프로그램 사용도 같은 흐름을 쓴다.

### 철학을 실제 동작으로 옮기기

| 제공된 TempleOS 해석에서 채택한 원칙 | 작업대의 결정 |
| --- | --- |
| 불필요한 표현을 줄이고 판단에 필요한 구조를 남긴다 | 대상·요청·현재 동작·변경·검사만 기본 노출. 세부 도구 출력과 내부 ID는 펼쳐 보기 |
| 사용자가 의미를 직접 구성한다 | “여기”를 실제 파일·범위에 고정. 요구와 보존 조건을 수정할 수 있게 유지 |
| 명령과 결과가 가까이 있다 | 작업 대상 옆에 요청란, 바로 아래에 해당 실행의 변경과 검증 |
| 인간의 판단 지점을 보존한다 | 대상이 낡았거나 권한 범위가 바뀌거나 복원이 다른 변경을 덮을 때 명확히 드러냄 |
| 불필요한 마찰은 줄인다 | 명령어 암기, 매 도구 호출 승인, 장식적 진행률, 의미 없는 대기 시간은 추가하지 않음 |

이는 사용자가 제공한 해석을 제품에 적용한 것이다. Terry Davis의 역사적 의도나 인지 효과를 입증한다는 뜻이 아니다.
생성되는 사용자 앱의 디자인은 요청에 따른다. Pida의 절제된 외형을 강제하지 않는다.

## 2. 현재 코드와의 차이

이번에는 아래 경로의 코드를 읽어 대조했다. 이 표의 ‘있음’은 코드 경로 확인이며 이번 턴의 실모델 시험 결과가 아니다.

| 항목 | 0.8.8에 있는 연결 | 이번 설계에서 필요한 연결 |
| --- | --- | --- |
| 실행 소유 | 호스트가 Pi 세션, 도구, 권한, 실행을 소유. Web/TUI는 HTTP 클라이언트 | 그대로 재사용 |
| Web 작업대 | Studio의 미리보기/파일/변경, 옆 대화, 템플릿, manifest 검사 표시 | 선택 대상을 구조화하고 요청·실행·변경에 계속 연결 |
| TUI 작업대 | Pi TUI 컴포넌트, F5 파일 선택·읽기, F6 Git diff, 실행/도구 결과 | 읽은 파일·행 범위를 요청에 고정하고 대상 패널과 입력을 함께 유지 |
| 화면 간 연속성 | 주 작업 공간 Web/TUI의 같은 세션 조회·관찰 | Studio까지 정확한 세션·대상·review ID로 열기 |
| Studio의 상태 | 별도 세션 ID와 review 정보를 탭의 `sessionStorage`에 보관 | 접수된 작업 대상과 review 기준을 호스트에서 복원 가능하게 보관 |
| 파일 버전 | 프로젝트 파일 읽기에 revision이 있음. workbench 파일 읽기는 path/content 반환 | workbench 파일의 내용·해시를 같은 읽기에서 반환. 해시 종류 구분 |
| 변경 비교 | workbench 전후 checkpoint, 프로젝트의 현재 Git diff | 실행 접수 경계와 종료 경계에 기준을 묶기. 프로젝트 diff를 실행 전후 변경으로 오인하지 않게 표시 |
| 검증 | ResultManifest의 산출물 해시·검사 결과·UNKNOWN 판정 | 동일한 projection을 두 화면에서 쓰고 이후 파일 수정 시 ‘이전 버전 검사’ 표시 |
| 도구 확장 | 도구/구성 정보, MCP·프로그램 프록시 등 기존 연결 | 사용 가능한 기능을 대상 옆에서 발견. 미설치 기능은 실제 설정 경로 안내 |

주요 근거: `examples/web/studio.js`, `src/tui.ts`, `src/tui-controller.ts`, `src/client.ts`,
`src/http.ts`, `src/ui-frame.ts`, `src/project-view.ts`, `src/project-tools.ts`,
`src/execution-contract.ts`, `docs/WORKBENCH.md`, `docs/TUI.md`.

**같은 호스트에 연결되어 있다는 사실만으로 작업 대상까지 공유되는 것은 아니다.**
현재 Studio의 선택 파일은 주로 모델에 전달하는 문자열 맥락이고,
TUI의 파일은 읽기 패널이다. 두 경로 모두 구조화된 대상 고정이 필요하다.

## 3. 공통 사용 흐름

1. **본다:** 서비스 화면, 파일, 변경 부분, 도구 결과 중 하나를 연다. 열기만 해서는 모델을 호출하지 않는다.
2. **고정한다:** ‘요청 대상으로 사용’을 누른다. 입력란 위에 파일/범위와 확인한 버전이 남는다.
3. **요청한다:** 자연어로 추가·수정·설명·검사를 요청한다. 보존 조건은 선택 입력이며 반복 입력을 강요하지 않는다.
4. **따라본다:** 접수, 모델 응답 대기, 실제 도구명, 변경된 파일, 검사 실행을 사실대로 표시한다.
5. **판단한다:** 실제 diff, 화면, 검사 결과를 본다. ‘이 변경을 기준으로 이어가기’로 현재 버전을 읽어 다음 요청에 고정한다.

보기 선택과 요청 대상은 다르다. 실행 중 다른 파일을 둘러봐도 이미 접수된 요청의 대상은 바뀌지 않는다.
입력 중에도 다른 파일을 열었다고 초안 대상이 자동 교체되지 않는다. 교체 동작은 눈에 보이는 한 번의 선택이다.
대상 없이 일반 질문을 하는 기존 경로도 유지한다.

### 예: 점검 알림 추가

| 순간 | 사용자가 보는 것 | 호스트가 기록하거나 확인할 것 |
| --- | --- | --- |
| 대상 고정 | `app/index.html · 탐색 메뉴 · 확인한 버전` | 최초에는 파일/실제 소스 범위. DOM 위치 선택은 후속 단계 |
| 요청 | “점검 알림 메뉴와 목록을 추가해줘. 검색·필터 유지” | 원문 요청과 허용된 참조를 기존 개인 세션 경계 안에 보관 |
| 진행 | `파일 읽는 중` → `파일 변경` → `검사 실행` | 실제 run/tool 이벤트. 모델이 말한 계획과 실행 사실을 구분 |
| 결과 | 어느 파일/행이 바뀌었는지, 어디서 알림을 여는지 | before/end 참조와 manifest. 기준 확보 실패도 명시 |
| 확인 | ‘메뉴는 보임 / 클릭 검사 통과 / 실제 설비 연동 미검증’ | 화면 로드, 범위 한정 검사, 사용자의 확인을 서로 다른 사실로 유지 |
| 후속 | “이 목록에 상태 필터도 붙여줘” | 이전 요청 대상을 맹목적으로 재사용하지 않고 현재 파일을 다시 확인 |

## 4. Web 작업대

### 구성

| 영역 | 기본 내용 | 상호작용 |
| --- | --- | --- |
| 상단 | 작업 공간, 현재 세션, 실제 실행 상태 | 세션 선택. 같은 작업을 TUI에서 여는 정확한 참조 제공 |
| 왼쪽 좁은 탐색 영역 | 파일/작업 대상 목록 | 열기, 경로 이동. 좁은 창에서는 접어서 사용 |
| 중앙 주 작업 영역 | 화면 / 소스 / 변경 / 결과 | 같은 대상의 표현 전환. 파일 선택·범위 선택. 화면은 데스크톱/모바일 전환 |
| 오른쪽 요청 영역 | 고정한 대상, 요청, 선택적 보존 조건, 대화 | 대상 교체/해제, 전송, 실행 중 추가 지시·다음 요청·중단 |
| 하단 결과 영역 | 변경 파일, 저장/미리보기/검사 상태 | diff·검사 출력·이전 버전 열기. 복원은 범위와 조건 확인 후 실행 |

중앙 작업 영역을 가장 넓게 둔다. 기본 비율은 탐색 약 16%, 작업 약 53%, 요청 약 31%에서 시작해 실사용으로 조정한다.
넓이가 부족하면 탐색을 접고, 더 좁아지면 작업/요청을 전환한다. 이때 요청 대상과 실행 상태는 항상 남긴다.
`의도/구조/실행/판단`을 네 개의 큰 고정 카드로 만들지 않는다. 목표는 입력에,
구조는 대상과 변경 관계에, 실행은 상태에, 판단은 diff와 근거에 배치한다.

### 화면을 가리켜 요청하기

- 첫 납품: 현재 앱 파일 또는 소스 범위를 고정. 미리보기는 옆에서 계속 볼 수 있다.
- 후속 납품: 명시적으로 켜는 ‘화면에서 선택’ 모드. 선택 모드가 꺼져 있으면 앱 클릭은 앱의 실제 동작을 수행한다.
- 호스트가 읽은 HTML 버전에서 만든 위치 매핑이 있는 요소만 정확한 소스 범위로 승격한다.
- 동적 DOM 등 매핑이 없으면 ‘화면 위치 참고’로 표시하고 파일 단위 대상과 구별한다.
- 선택 표시용 정보는 렌더링 복사본에만 넣고 서비스 원본을 임의 수정하지 않는다.
- 기존 opaque-origin iframe 격리와 CSP를 유지한다. 메시지의 source, render ID, 문서 revision, 크기/형식을 검증한다.
  프레임이 보내는 selector·텍스트·‘검사 통과’ 주장은 신뢰된 권한이나 검증 근거가 아니다.

Web에서 기존 파일 수정은 즉시 저장된다. 별도의 staging 구현 없이 ‘적용 전 미리보기’나 ‘승인하면 반영’이라고 표시하지 않는다.
설치된 브라우저 검사 도구가 없으면 ‘미실행’으로 표시하고 사용 가능한 검사 범위를 설명한다.
일반 프로젝트의 dev server 미리보기는 기존 단일 HTML 서비스 미리보기와 별도 능력이다. URL을 임의로 실행하거나 격리를 완화하지 않는다.

## 5. TUI 작업대

텍스트 기반 작업 대상이 대화 옆에 실제로 남는 터미널 작업대를 만든다.
기존 Pi `Editor`, `SelectList`, `ScrollView`, 가로/세로 레이아웃과 마우스 지원을 재사용한다.
브라우저 DOM과 자유 배치 편집기를 터미널 안에 구현하지 않는다.

| 터미널 너비 | 설계 |
| --- | --- |
| 120열 이상 | 좁은 파일 목록 + 넓은 파일/변경/출력 + 요청·대화. 파일 목록은 접을 수 있음 |
| 90–119열 | 파일/변경과 요청의 두 영역. 파일 목록은 F5 선택창 |
| 90열 미만 | 대상 보기 / 요청 보기 전환. 고정 대상·실행 상태·전송/중단 동작은 유지 |

이는 다음 작업대의 제안 기준이다. 현재 0.8.8의 개요 패널 기준인 104열과 혼동하지 않는다.
폰트를 줄여 정보를 우겨 넣지 않으며 CJK 표시 폭, 줄바꿈, 터미널 resize를 실제로 검증한다.

### 키와 선택

| 동작 | 설계 |
| --- | --- |
| 기능 찾기 | 기존 F1 메뉴와 보이는 버튼 유지. 모든 새 동작은 여기서 접근 가능 |
| 세션·실행·도구 | 기존 F2 / F3 / F4 유지 |
| 파일 열기 | F5. 읽은 파일을 주 작업 패널에 남김 |
| 변경 보기 | F6. 실행 전후 / 현재 전체 Git 변경을 명시적으로 구별 |
| 개요·밀도 | F7 / F8 유지 |
| 대상 고정 | F1의 ‘요청 대상으로 사용’이 기준 동작. F9는 충돌 검증 후 보조 단축키 후보 |
| 행 범위 지정 | 파일 줄 번호 선택 또는 작은 시작/끝 행 입력창. F1에서 발견 가능 |
| 요청 입력 | 기존 Enter 전송, Shift+Enter/Alt+Enter 줄바꿈 유지. 한글 조합 중 전송 방지 |
| 화면 미리보기 | 같은 세션·대상·review를 Web에서 열기. 터미널에는 연결 상태와 참조 유지 |
| 중단·분리 | 기존 관찰한 run ID에 대한 중단과 UI 분리를 구별 |

행 선택은 읽기/참조 기능이다. 완전한 코드 에디터를 새로 만드는 것이 선행 조건은 아니다.
코드 수정은 기존 허용된 에이전트 도구로 진행한다. 직접 편집이 필요해지면 별도 결정으로 취급한다.

## 6. 호스트의 최소 공통 계약

두 UI가 각자 프롬프트를 조립해 의미가 갈라지지 않도록 대상 해석과 결과 projection을 공유한다.
**Pi 실행 루프는 그대로 둔다.** 이 계약은 Pida의 인증된 작업 공간 어댑터/HTTP 계층에 둔다.
범용 runtime에 Web DOM이나 특정 앱 구조를 필수 필드로 넣지 않는다.

### 6.1 세 종류의 선택

| 선택 | 수명/소유 | 규칙 |
| --- | --- | --- |
| `viewSelection` | 현재 클라이언트 | 자유롭게 탐색. 모델 실행·대상 교체를 일으키지 않음 |
| `draftBinding` | 해당 클라이언트의 초안 | 명시적으로 고정/교체. 보내지 않은 초안은 자동으로 다른 창에 복사하지 않음 |
| `acceptedBinding` | 호스트가 접수한 실행 기록 | session/run에 묶인 불변 참조. Web/TUI가 같은 기록 조회 |

초안 보존은 해당 클라이언트의 제한된 로컬 저장 규칙을 따른다. Web에서 TUI로 초안 자체를 넘기는 기능은 1차 범위에서 제외한다.
이미 접수한 요청과 검토 결과는 호스트 저장으로 이어진다. 세션 선택이나 관찰만으로 새 실행을 생성하지 않는다.

### 6.2 대상 참조 초안

아래는 검토 가능한 제안 타입이다. 현재 API에 이미 존재하는 타입이 아니다.

```ts
type WorkTarget = {
  kind: "file" | "source-range" | "tool-result";
  resource: "workbench" | "project" | "run";
  path?: string;               // 호스트가 허용한 상대 경로만
  contentSha256?: string;      // 실제 읽은 파일 바이트의 해시
  range?: { startLine: number; endLine: number }; // 1부터, 끝 포함
  sourceRunId?: string;
  sourceToolCallId?: string;
};

type WorkBinding = {
  schemaVersion: 1;
  id: string;                  // 호스트 발급 opaque ID
  sessionId: string;
  targets: WorkTarget[];       // 첫 UI는 주 대상 1개, 명시적 관련 참조만 추가
  resolvedAt: string;
};
```

- 위 필드의 허용 조합은 실제 구현에서 discriminated union/schema로 고정한다.
  파일은 path/hash 필수, 범위는 범위/hash 필수, 도구 결과는 소유한 원본 run/call 참조 필수다.
- owner와 실제 workspace identity는 인증과 서버 설정에서 도출한다. 클라이언트가 임의의 루트나 owner를 지정하지 못한다.
- CRLF/LF를 바꾸기 전 원본 바이트를 해시한다. 행은 같은 바이트를 디코드한 결과에 붙인다. 내용이 바뀌면 기존 범위를 자동 재해석하지 않는다.
- 파일/행 범위, 표시용 Git diff revision, workbench 전체 revision, 검사 artifact snapshot digest는 서로 다른 종류다. 이름을 통일해 섞지 않는다.
- 도구 출력은 허용된 기록에서 제한된 분량을 읽는다. 원문 전체를 공통 trace/관측 export에 복제하지 않는다.
- 화면 요소 선택은 후속 어댑터가 파일/범위로 해석한다. 매핑 실패는 비정형 참고로 표시하며 파일 참조를 위조하지 않는다.
- 요청 target은 **작업 맥락이지 파일 쓰기 권한이 아니다.** 허용된 관련 파일을 수정할 수 있음을 표시한다.
  기존 프로젝트 shell은 OS sandbox가 아니며 선택 파일만 쓰게 제한했다고 주장하지 않는다.

### 6.3 접수와 변경 기준

기존 `/sessions/:id/runs`와 `PidaClient.stream()`의 선택적 확장을 우선한다.
구체적인 route 명칭보다 아래 계약을 먼저 고정한다. 대상 없는 기존 요청은 계속 동작한다.

1. 기존 권한 검사와 실행 admission/gate 안에서 대상 소유·현재 해시·범위를 확인한다.
2. 비교 기준을 확보하고, `acceptedBinding`과 기존 run ID를 연결한다.
3. 기존 Pi 실행으로 위임한다. 클라이언트의 임의 system instruction이 아니라 호스트가 해석한 참조 맥락을 전달한다.
4. 종료 때 같은 기록에 변경/검증 참조를 연결한다. 성공·실패·취소 모두 실제 남은 변경을 보여 준다.
5. 이미 돌아가는 기록을 다시 여는 것은 조회다. 네트워크 불확실성이 새 실행을 자동 재전송하지 않게 한다.

파일이 달라졌으면 모델 호출 전에 `TARGET_STALE` 같은 구별 가능한 응답과 ‘최신 내용 확인’을 제공한다.
초안은 보존한다. 무조건 거절하고 막는 대신 새 버전 차이를 보고 한 번에 다시 고정할 수 있게 한다.
접수 직전 검사는 외부 에디터와의 영구 잠금을 보장하지 않는다. 접수 뒤 생기는 변경도 기존 도구의 충돌 검사와 끝 시점 재확인으로 드러낸다.

중복 접수 식별은 기존 실행/effect receipt 설계를 재사용하되 요청 접수까지 실제로 보호되는지 조사한다.
필요하면 owner/session에 묶인 client request ID와 payload digest를 보완한다.
같은 ID·같은 요청은 기존 접수 결과를 조회하고, 같은 ID·다른 요청은 충돌로 처리한다.
호스트 crash 후 접수 여부가 불확실하면 조회/복구 상태를 반환하며 자동 재실행하지 않는다.
이것은 외부 변경의 exactly-once 보장이 아니다.

### 6.4 공통 review projection

| 정보 | 출처와 의미 |
| --- | --- |
| 세션/실행/작업 | 기존 session/run/task ID를 유지. 새로운 Mission 엔진 없음 |
| 접수한 대상 | acceptedBinding. 현재 보고 있는 파일과 구별 |
| 비교 기준 | 기준 확보 시각·종류·참조 또는 unavailable 사유 |
| workbench 변경 | 기존 전후 checkpoint. 실행 구간 동안 관찰한 파일 집합 차이이며 모든 차이의 인과적 귀속을 보장하지 않음 |
| project 변경 | 기본은 기존 `git-staged-and-working-tree` / `displayed-diff`. run 전후 실제 파일 바이트가 확보된 항목만 별도 before/end hash 표시 |
| 저장/표시 | 실제 파일 revision과 renderer acknowledgement. 저장 또는 표시가 검사 통과를 뜻하지 않음 |
| 검사 | 기존 manifest의 definition/artifact digest, 시각, 범위, 상태, 현재 버전 일치 여부 |
| 사용자 확인 | 사용자가 화면을 확인했다는 별도 기록. 독립 검증으로 승격하지 않음 |
| 실행 결과 | 기존 completed/failed/cancelled/limited/interrupted. 검사 UNKNOWN과 별개 |

파일이 검사 이후 바뀌면 ‘통과’만 남기지 않고 ‘이전 버전에서 통과’로 표시한다.
현재 해시를 읽을 수 없으면 ‘현재 일치 여부 확인 불가’다.
agent-supplied check 통과와 독립적인 과제 검증은 계속 구분하며, 모델의 완료 선언으로 `VERIFIED`를 만들지 않는다.
review 기록이나 관측 저장에 실패해도 정상적인 에이전트 실행을 무조건 중단시키지 않는다.
이미 확보하지 못한 실행 전 기준을 종료 뒤 현재 파일로 꾸며 채우지 않는다.

### 6.5 저장과 화면 간 이동

- 기존 실행 기록/manifest 참조와 함께 작은 private binding/review 기록을 보관한다. 별도의 에이전트 상태 머신을 만들지 않는다.
- 원문·선택 내용·도구 출력은 기존 개인 세션 권한 경계 안에 두며 공통 Observation export에 자동 추가하지 않는다.
- Web에서 ‘터미널로 이어보기’, TUI에서 ‘웹에서 보기’는 같은 host/session/binding/review를 가리킨다.
  URL/명령에는 opaque ID만 넣고 credential·프롬프트·원문을 넣지 않는다.
- 링크를 열어도 인증과 소유권을 다시 확인한다. 다른 host나 없는 session이면 새 세션으로 조용히 대체하지 않는다.
- Studio의 기존 세션은 보존한다. 새 링크가 정확한 session을 지정하면 해당 Studio 문맥으로 연다.
- 기존 탭 로컬 review는 legacy로 읽을 수 있지만 호스트 기준으로 사후 검증되지 않으면 ‘이 브라우저의 기록’으로 표시한다.
- detach/reconnect는 실행을 재시작하지 않는다. 서버 종료와 UI 종료는 다르다.

## 7. 상태와 사용자 행동

| 상황 | 표시 | 가능한 다음 행동 |
| --- | --- | --- |
| 대상 없음 | 일반 요청 | 그대로 질문 / 파일 열고 고정 |
| 고정됨 | 대상·범위·버전 | 요청 / 교체 / 해제 |
| 대상이 바뀜 | 최신 파일과 다름 | 차이 확인 후 다시 고정, 초안 유지 |
| 접수 여부 불명 | 연결 복구 중, 자동 재전송 안 함 | 서버에서 접수 결과 조회 |
| 실행 중 | 실제 tool/model/command 상태와 마지막 이벤트 시각 | 둘러보기 / 추가 지시 / 다음 요청 / 중단 |
| 중단 처리 중 | 취소 요청, 외부 변경 잔존 가능성의 실제 상태 | 실제 종료와 저장 파일 확인 |
| 종료 | 실행 결과 + 변경 + 검사/미검증 | 현재 버전으로 이어가기 / 근거 보기 / 조건에 맞는 복원 |
| 검사 이후 수정 | 이전 버전 검사 | 새 검사 요청 |

관찰 정보가 없으면 현재 단계나 완료 백분율을 만들어 내지 않는다.
실행 중 추가 지시는 현재 run에 묶고, 새 대상 변경은 별도의 명시적 참조로 취급한다.
대기 중 follow-up의 메모리 내 수명은 현재 구현의 한계를 그대로 표시한다.
이를 이번 작업에서 durable mission queue로 확대하지 않는다.

## 8. 필요한 기능 붙이기

‘붙이기’는 두 동작으로 구분하되 작업 흐름에서는 가까이 둔다.

- **산출물에 기능 추가:** 화면/파일을 고정해 자연어로 요청. 이미 허용된 도구로 구현한다.
- **에이전트에 능력 연결:** 사용 가능한 도구 목록에서 현재 등록·허용·제약을 확인하고 기존 설정 경로로 이동한다.

초기에는 기존 구성/도구 조회, 템플릿, 스킬, MCP, 등록된 프로그램 프록시를 재사용한다.
검색된 저장소가 있다는 이유만으로 자동 설치하거나 실행 권한을 주지 않는다.
도구가 없을 때 실제 부족한 기능과 설정 위치를 알려 주며, 빈 목록을 ‘지원 완료’로 포장하지 않는다.
기존 private provider 모듈도 호스트 설정을 그대로 사용한다. Web/TUI마다 별도 OAuth나 회사 인증 구현을 만들지 않는다.

능력 목록은 기본 화면의 상시 큰 패널이 아니라 F4/작업 메뉴에서 연다.
파일·실행 결과·등록된 도구가 새 종류로 늘어도 대상 resolver와 viewer를 추가하면 되고,
Pi 실행 루프나 다른 앱을 수정하지 않는 경계를 지킨다.

## 9. 구현 패치 순서

패치 ID는 이 설계의 로컬 작업 번호다. 아래 버전은 확정 릴리스 약속이 아니다.
첫 동작 단위를 완성한 뒤 patch 버전을 올리고, 각 묶음은 별도 커밋으로 남긴다.

| 패치 | 변경/재사용 경로 | 완료 기준 |
| --- | --- | --- |
| WS-01 대상 계약 | `src/client.ts`, `src/protocol.ts`, `src/http.ts`, 기존 파일 읽기 어댑터; 작은 공통 target resolver | workbench/project 읽은 바이트와 hash 연결, 권한·경로·범위 검증, 기존 무대상 요청 호환 |
| WS-02 접수·review | 기존 실행 admission/gate, 실행 기록, checkpoint/manifest 연결. 저장은 작은 private sidecar 후보 | 원자적인 Pida 내부 접수 순서, stale면 tool call 0회, 기준 누락을 정직하게 표시, 재접수 중복 방지 |
| WS-03 Web 연결 | `examples/web/studio.js`와 기존 shell/stylesheet, 공통 SDK | 파일/범위 고정, 대상 바꾸기, 계속 보면서 요청, 같은 실행 diff·검사. 기존 Studio 세션 보존 |
| WS-04 TUI 연결 | `src/tui-controller.ts`, `src/tui.ts`, 공통 SDK; 기존 Pi 컴포넌트 | 지속 파일/변경 패널, 고정한 대상 옆 입력, 폭별 전환, 기존 키·IME·NO_COLOR 유지 |
| WS-05 연속성과 회복 | 양쪽 진입/관찰 코드, private review 조회 | Web→TUI→Web에서 같은 대상·실행·근거. 재시작/취소/오프라인 뒤 재실행 없이 복원 |
| WS-06 화면 요소 선택 | `src/ui-frame.ts`, Studio, 버전별 source mapping 어댑터 | 선택 모드 분리, 정확한 소스 위치 또는 명시적 mapping unavailable, 조작된 frame 메시지 거부 |
| WS-07 통합 수용 | 기존 browser/PTY/API 검증 runner 확장, 문서 | 아래 시나리오의 자동/실모델/Windows 결과를 분리 기록하고 미통과 부분만 재검증 |

WS-01~05로 먼저 **파일/범위를 보면서 양쪽에서 이어서 작업하는 완결된 흐름**을 만든다.
WS-06의 DOM 매핑은 이후에 붙여도 첫 사용 흐름이 막히지 않는다.
WS-07의 검사는 마지막까지 미루는 뜻이 아니다. 각 단계의 핵심 회귀를 함께 실행하고 마지막에 한 번 통합 검토한다.

추정하지 않고 구현 직전에 확인할 지점: 기존 gate hook의 정확한 위치, 접수 key의 기존 적용 범위,
private record 저장 재사용 가능성, Pi TUI의 범위 선택/포커스 지원, source mapping에 재사용할 설치된 parser.
이 확인 때문에 Pi 버전을 먼저 올리거나 새 UI 프레임워크를 도입하지 않는다.

## 10. 수용 시험

| 시험 | 관찰 가능한 통과 조건 |
| --- | --- |
| 대상 고정 | 파일 A를 고정하고 B를 열어도 요청은 A에 남음. A가 접수된 후 B 보기로 바꿔도 run 대상 불변 |
| 내용 충돌 | 선택 뒤 파일 수정 → stale 응답, 모델/도구 미실행, 초안 유지, 최신 내용 재고정 가능 |
| 실제 기능 추가 | 설비 화면에 점검 알림 메뉴/목록 추가 → 화면에서 위치 확인, 실제 클릭, 검색/필터 보존 검사 |
| 일반 코드 수정 | 프로젝트 파일·관련 테스트 수정 → 실제 테스트 exit/output 확인, 기존 사용자 변경 보존 |
| 양방향 연속성 | Web에서 실행 → TUI에 같은 ID·대상·도구 상태 → Web에서 같은 review 열기. 새 모델 요청 없음 |
| 비교의 정직성 | 초기 사용자 Git 변경/외부 파일 변경이 섞여도 전체 diff를 run의 단독 변경으로 표시하지 않음 |
| 검사의 신선도 | 검사 뒤 같은 파일 수정 → 이전 검사 표시. read 실패 → 현재 일치 여부 unknown |
| 취소/연결 끊김 | 파일 변경 뒤 취소/분리 → 실제 잔존 변경 확인. cancelled를 completed로 승격하지 않음 |
| 재접수·재시작 | 응답 유실/호스트 재시작 뒤 기존 접수 조회. 불확실한 외부 효과를 중복 실행하지 않음 |
| 권한·프레임 | 다른 owner/session, 경로 탈출, 낡은 render ID, 조작된 선택 메시지 거부. 비밀값/원문 공통 로그 노출 없음 |
| 좁은 화면·입력 | Web 320/768/1440px, TUI 80/104/140열, 한국어 조합/붙여넣기/resize. 대상·전송·중단 접근 유지 |
| 원래 기능 | 무대상 일반 질문, 템플릿, 세션 복원, compaction/handoff, 도구 설정과 프로젝트 권한 회귀 없음 |

모델 판단을 script로 고정한 실제 Pi/API/도구 시험, 실제 브라우저, 실제 터미널 PTY,
실모델, 사용자 Windows 터미널을 각각 기록한다. 어느 하나로 다른 층을 통과 처리하지 않는다.
실모델은 현재 사용 가능한 provider를 사용한다. 회사 게이트웨이의 추가 인증 세부는 요청하지 않으며 기존 private connector로 시험한다.
실행하지 못한 환경은 NOT_RUN이다. 테스트 수보다 사용자가 대상·변경·검증을 이어 볼 수 있는지로 수용한다.

## 11. 이번 산출물의 완료 범위

- **계획:** 코드 대조, UX, 공통 데이터 경계, 패치 순서, 수용 기준 작성.
- **구현:** 문서와 대화 내 동작 시안만. WS-01~07 runtime/UI 기능은 미구현.
- **시험:** 설계 문서/시안 정합성 확인 범위. 시안의 예시 데이터는 실행 증거가 아님.
- **실제 통합:** 이번 설계에 대한 live LLM, Windows, 회사 API, Web/TUI 연속 작업 시험은 미실행.

대화 내 시안은 Web/TUI 두 표현에서 파일 열람, 요청 대상 고정, 행 범위 선택,
클라이언트별 미전송 초안, 접수한 요청 표시, 변경 예시, 새 버전으로 이어가기를 비교한다.
마크업·입력 label/ID·JavaScript와 12개 상호작용 시나리오를 DOM fixture로 확인했다.
이는 실제 브라우저 레이아웃·Pida 실행 시험이 아니다. 현재 환경에 Chromium 실행 파일이 없어
시안의 실제 브라우저 렌더링 검사는 NOT_RUN이다. runtime 코드를 바꾸지 않아 기존 전체 테스트를 재실행하지 않았다.

기존 기능의 검증 기록은 [0.8.8 문서](TUI-0.8.8.md)와 [TUI 검증](TUI-VALIDATION.md)에 별도로 있다.
다른 앱의 변경이 필요하도록 설계하지 않았다. Schumpeter, Memory Substrate, PIX 구현은 이번 범위에 포함하지 않는다.
